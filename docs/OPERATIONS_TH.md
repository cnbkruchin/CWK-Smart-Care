> ตัวเลขโควตา/ข้อจำกัดของ Google ที่อ้างถึงต้องตรวจกับเอกสารปัจจุบันก่อนใช้ (INSTALL_GAS_TH §0) — เอกสารนี้ไม่รับรองตัวเลขแทนผู้ให้บริการ

## 3. การสำรองข้อมูล (backup)

- **อะไรถูกสำรอง**: สำเนาของ master workbook และ workbook ทุกภาคเรียน (คัดลอกขณะถือ ScriptLock จึงเป็นจุดเวลาเดียวกัน), Script Properties ที่ไม่ใช่ความลับ (`config.json`), รายการไฟล์แนบพร้อม SHA-256 (`attachments-manifest.json`), และ `manifest.json` (จำนวนแถวต่อชีต; SHA-256 ของ manifest บันทึกใน BackupRuns)
- **อะไรไม่ถูกสำรองในสำเนาประจำคืน**: ความลับ (ต้องเก็บแยกตามนโยบายของโรงเรียน), เนื้อไฟล์แนบ (อยู่ในโฟลเดอร์ส่วนตัวเดิม — การส่งออกแบบพกพาในชุดที่ 6 คัดลอกไฟล์จริง)
- **ที่เก็บ**: `<โฟลเดอร์ส่วนตัวของระบบ>/backups/<วันที่>-<รหัส>` ไม่แชร์; เก็บ `backup.retention_days` วัน (ค่าเริ่มต้น 30) แล้วย้ายลงถังขยะ
- **เวลา**: `backup.nightly_time` (01:30) — ระหว่างคัดลอก ผู้ใช้ที่บันทึกข้อมูลอาจต้องรอ lock จึงตั้งในช่วงไม่มีผู้ใช้
- **สั่งทันที**: หน้า "สถานะระบบ" → "สำรองข้อมูลตอนนี้" (ผู้ดูแลระบบ)
- **RPO/RTO**: โรงเรียนเลือกเองหลังวัดเวลาจริง — สำรองรายวัน **ไม่ป้องกันข้อมูลที่เกิดระหว่างวัน** (สูงสุดเกือบ 1 วัน) ถ้าต้องการน้อยกว่านี้ให้เพิ่มความถี่ (คำนึงถึงโควตา Drive และเวลาที่ถือ lock) หรือย้าย backend (ชุดที่ 7)

## 4. ทดสอบ restore (ต้องทำอย่างน้อยหนึ่งครั้งก่อนใช้งานจริง)

1. สร้างโปรเจกต์ Apps Script **ใหม่** (environment STAGING/DR) ด้วยบัญชีเจ้าของเดียวกัน แล้ววางโค้ดจาก gas-dist (INSTALL §4–5) — **ห้าม restore ทับระบบจริง** (ระบบปฏิเสธเมื่อมีข้อมูลอยู่แล้ว)
2. Script Properties: `CWK_ENV=STAGING`, `CWK_ADMIN_TASKS_ENABLED_UNTIL` (≤ 2 ชม.), `CWK_RESTORE_FROM_FOLDER_ID=<id ของโฟลเดอร์สำรอง>`
3. รัน `adminRestoreSnapshot` → ระบบคัดลอก workbook, ชี้ StorageCatalog ไปยังสำเนาใหม่, ตั้ง `CWK_MASTER_SPREADSHEET_ID`/`CWK_DRIVE_ROOT_FOLDER_ID`, เทียบจำนวนแถวกับ manifest (`row_count_check: OK` / `MISMATCH` พร้อมรายการ)
4. ใส่ secrets ของ environment ใหม่, รัน `adminSchemaCheck`, `adminInstallTriggers`, deploy และตรวจหน้าหลัก/รายงาน R01 ของวันที่สำรอง
5. จับเวลาตั้งแต่ข้อ 1 ถึงใช้งานได้ แล้วบันทึกในระบบต้นทาง: สถานะระบบ → การสำรองข้อมูล → "บันทึกผลทดสอบ restore" (ผล PASS/FAIL, นาที, สิ่งที่ตรวจ) — หน้าสถานะระบบจะแสดง FAIL ใน PROD จนกว่าจะมีบันทึกนี้
6. ไฟล์แนบ: ถ้า environment ใหม่เป็นบัญชีอื่น ใช้ portable export (ชุดที่ 6) เพื่อคัดลอกไฟล์จริง

## 5. ระยะเวลาเก็บข้อมูล (retention)

| กลุ่มข้อมูล | ระยะเก็บ (ค่าเริ่มต้นใน schema) | ระบบทำอะไร |
|---|---|---|
| IdempotencyRecords, MutationJournal | 30 วันหลังจบภาคเรียน | ผู้ดูแลกด "ล้างตามระยะเก็บ" ต่อภาคเรียน (audit) |
| WebhookInbox | 90 วันหลังจบภาคเรียน | เช่นเดียวกัน |
| OperationMetrics, NotificationAttempts | 1 ปีหลังจบภาคเรียน | เช่นเดียวกัน |
| Jobs ที่จบแล้ว | 90 วัน | ผู้ดูแลกด "ลบงานเก่า" (audit) |
| สำเนาสำรอง | `backup.retention_days` (30 วัน) | ย้ายลงถังขยะอัตโนมัติหลังสำรองครั้งใหม่สำเร็จ |
| ข้อมูลนักเรียน การมาเรียน ใบลา เรื่องติดตาม การติดต่อ Audit ไฟล์แนบ | ตาม retention class ใน DATA_DICTIONARY (เช่น ENROLLMENT_PLUS_5Y, AUDIT_5Y) | **ไม่ลบอัตโนมัติ** — ต้องมีนโยบายเป็นลายลักษณ์อักษรและการอนุมัติของโรงเรียนก่อน (กระบวนการลบข้อมูลส่วนบุคคลยังไม่ส่งมอบในระยะแรก) |

- ข้อมูลที่ลบแล้วยังอยู่ในสำเนาสำรองจนกว่าสำเนานั้นหมดอายุ — ระยะเก็บสำเนาต้องสอดคล้องกับนโยบาย
- คำขอแก้ไข/ลบข้อมูลจากเจ้าของข้อมูล: บันทึกคำขอ ตรวจสิทธิ์ และใช้การแก้ไขที่มีเหตุผล (audit) — ดู PRIVACY_NOTICE_DRAFT_TH

## 6. เหตุขัดข้องและวิธีรับมือ

| อาการ | ตรวจ | ทำ |
|---|---|---|
| หน้าเว็บบันทึกไม่ได้ "ระบบไม่ว่าง (LOCK_TIMEOUT)" บ่อย | สถานะระบบ → lock wait p95, งานที่รันช่วงนั้น (สำรอง/รายงานใหญ่) | เลื่อนงานหนักไปนอกเวลา, ลดขนาดรายงาน, ดูหัวข้อ 7 |
| `journal.pending` = FAIL (RECOVERY_REQUIRED) | Executions log ของ cronTick | เปิดโหมดอ่านอย่างเดียว → รัน `adminRecoverJournal` → ตรวจ `adminSchemaCheck` → ถ้ายังไม่หาย restore ไป environment ใหม่จากสำเนาล่าสุดเพื่อตรวจ แล้วติดต่อผู้พัฒนา |
| cronTick ไม่ทำงาน | สถานะระบบ → triggers.cronTick | รัน `adminInstallTriggers` ด้วยบัญชีเจ้าของ |
| ข้อมูลผิดจำนวนมาก (นำเข้าผิด/แก้ผิด) | R11 Audit ช่วงเวลานั้น, ImportBatches | เปิดโหมดอ่านอย่างเดียว; แก้ด้วยการแก้ไขที่มีเหตุผล หรือ restore ไป environment ใหม่เพื่อเทียบ — **ห้ามแก้ใน Sheets ตรง ๆ** (ข้าม journal/audit) |
| แจ้งเตือนไม่ออก | ติดตามการส่งแจ้งเตือน: สาเหตุ (`NON_PROD_NOT_ALLOWLISTED`, `QUIET_HOURS`, `EMAIL_QUOTA`, `PROVIDER_NOT_CONFIGURED`, HTTP 4xx/5xx) | แก้ค่าตั้งตามสาเหตุ แล้วใช้ "ส่งซ้ำแบบเดิม"/"ส่งใหม่" |
| LINE webhook ล้มเหลว | Cloud Run log (`line_webhook` status 503), WebhookInbox | ดู GATEWAY_TH §8; LINE จะส่งซ้ำถ้าเปิด redelivery |
| เข้าสู่ระบบไม่ได้ทั้งโรงเรียน | gateway `/healthz`, Firebase console | ตรวจ Cloud Run/Secret; อย่าเปิด DEMO mode ใน PROD (ระบบปฏิเสธ) |
| สงสัยบัญชีถูกยึด | R11 Audit ของผู้ใช้ | ระงับบัญชี (มีผลทันที), เพิกถอน session (Firebase), ยกเลิกการผูก LINE, เปลี่ยน secret ที่เกี่ยวข้อง |
| ความลับรั่ว | — | เปลี่ยนค่าตามหัวข้อ 8 ทันที, ตรวจ log ช่วงที่เกี่ยวข้อง |

**โหมดอ่านอย่างเดียว**: สถานะระบบ → เปิด/ปิด (มีเหตุผล, audit) — server ปฏิเสธการบันทึกทุกช่องทาง ยกเว้นงานบำรุงรักษา

## 7. ประสิทธิภาพและเกณฑ์เริ่มย้ายระบบ

ดูในหน้าสถานะระบบ (OperationMetrics, flush ทุกรอบ cronTick; best effort) และ docs/CAPACITY.md

ตั้งเกณฑ์จากผล pilot ของโรงเรียนเอง ตัวอย่างสัญญาณที่ควรเริ่มย้ายไป REST + PostgreSQL (ชุดที่ 6–7) — **ไม่ใช่ตัวเลขรับรอง**:
- p95 ของ `attendance.recordArrival` ช่วงเช้าสูงกว่าเป้าที่โรงเรียนกำหนดติดต่อกันหลายวัน
- LOCK_TIMEOUT เกิดซ้ำในช่วงใช้งานสูง แม้เลื่อนงานหนักแล้ว
- คิวแจ้งเตือนค้างเกินชั่วโมงเป็นประจำ หรือใช้โควตาอีเมล/UrlFetch ใกล้เต็ม
- ขนาด workbook ใกล้เพดานเซลล์ (หน้าสถานะระบบ/CAPACITY)
- ต้องการ transaction/availability ที่ Sheets ให้ไม่ได้

## 8. การเปลี่ยนความลับ (rotation)

| ความลับ | วิธีเปลี่ยนโดยไม่หยุดระบบ |
|---|---|
| gateway identity secret | สร้าง key id ใหม่ + secret ใหม่ใน Secret Manager และ deploy gateway → เปลี่ยน `CWK_GATEWAY_KEY_ID`/`CWK_GATEWAY_SECRET` ใน Script Properties ให้ตรง (gateway รับ key id เดียว จึงเปลี่ยนสองฝั่งในช่วงเวลาสั้น ๆ นอกเวลาเรียน) |
| LINE envelope secret | เช่นเดียวกัน (`CWK_LINE_WEBHOOK_KEY_ID`/`CWK_LINE_WEBHOOK_SECRET`); ระหว่างเปลี่ยน LINE จะส่งซ้ำเหตุการณ์ที่ล้มเหลว |
| LINE channel secret / access token | ออกใหม่ใน LINE console → อัปเดต Secret Manager (gateway) / Script Properties (GAS) |
| `CWK_DEMO_PASSPHRASE` | เฉพาะ DEV/STAGING — เปลี่ยนเมื่อมีผู้ทดสอบออก |

## 9. Deploy และย้อนกลับ

INSTALL_GAS_TH §11: deploy เวอร์ชันใหม่บน deployment เดิม (URL เดิม) บันทึกเลขเวอร์ชันใน CHANGELOG; ย้อนกลับได้โดยเลือกเวอร์ชันก่อนหน้า **หลังตรวจว่าเวอร์ชันเก่ารองรับ schema_version ปัจจุบัน** — สำรองข้อมูลก่อน deploy ทุกครั้งที่มีการเปลี่ยน schema
